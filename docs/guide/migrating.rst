Migrating STIX 2.0 observed-data to STIX 2.1
============================================

STIX 2.0 stores cyber observables (SCOs) inside the ``objects`` mapping of an
observed-data object and links them with numeric string keys.  STIX 2.1 turns
those into standalone SCOs with real STIX IDs, referenced from observed-data
through ``object_refs``.  The :mod:`stix2.migration` package performs that
conversion on top of the existing STIX 2.1 object model.

The migrator never mutates its input, preserves the observation window,
``number_observed``, reference topology and migratable data markings, and
either raises or reports anything it cannot map 1:1 instead of silently
dropping data.

Migrating one observed-data object
----------------------------------

.. code-block:: python

    from stix2.migration import migrate_observed_data

    v20_observed_data = {
        "type": "observed-data",
        "id": "observed-data--8e9b2b22-1b9e-4f09-9b33-d0d4c9f0a111",
        "created": "2020-01-01T00:00:00.000Z",
        "modified": "2020-01-01T00:00:00.000Z",
        "first_observed": "2020-01-01T00:00:00.000Z",
        "last_observed": "2020-01-01T00:01:00.000Z",
        "number_observed": 3,
        "objects": {
            "0": {"type": "ipv4-addr", "value": "10.0.0.1"},
            "1": {"type": "network-traffic", "dst_ref": "0",
                  "protocols": ["tcp"]},
        },
    }

    result = migrate_observed_data(v20_observed_data)
    result.observed_data  # one STIX 2.1 observed-data using object_refs
    result.scos           # the standalone, de-duplicated SCO objects

Standalone SCOs receive deterministic UUIDv5 IDs generated by the STIX 2.1
object model.  Reordering the input never changes those IDs.  When a legal
reference cycle makes a deterministic ID impossible, the STIX 2.1 mandated
UUIDv4 fallback is used and the fact is reported.

Migrating a whole bundle
------------------------

:func:`stix2.migration.migrate_bundle` migrates every observed-data object,
carries marking-definition objects along so marking references stay
resolvable, de-duplicates shared SCOs across observations, and leaves distinct
observations distinct (two observations are never merged into one):

.. code-block:: python

    from stix2.migration import migrate_bundle

    result = migrate_bundle(v20_bundle)
    bundle = result.as_bundle()  # markings + standalone SCOs + observed-data

Strict versus lenient mode
--------------------------

By default the migrator is *strict* and raises
:class:`stix2.migration.MigrationError` for content that has no reliable 1:1
mapping, such as a missing reference target, an unrecognized non-custom
property, or a granular-marking selector scoped to the embedded ``objects``
mapping.

Pass ``strict=False`` to collect recoverable problems as
:class:`stix2.migration.MigrationIssue` records in ``result.issues`` instead;
the affected references or properties are then skipped rather than crashing
the run.  Problems with no safe STIX 2.1 representation remain blocking even
in lenient mode.

Use ``allow_custom=True`` to carry ``x_``-prefixed custom properties,
extensions and observable types over to STIX 2.1.  Non-custom unknown content
is always rejected, because there is no spec-backed place to store it.
